# Embedding model choice for `trace query --semantic`

## Intent

`bdtrace trace query --semantic` embeds a query and each trace's `record_text`
with sentence-transformers, defaulting to `all-MiniLM-L6-v2`. The corpus is
developer agent sessions: shell commands, file paths, code fragments and
natural-language prompts in one blob. MiniLM was trained on general web and NLI
text, not code, so the reasonable suspicion is that a code-aware or simply
larger encoder would retrieve better. This memo tests that suspicion against 138
real Claude Code sessions and reports what it measured, including the parts that
came out against the hypothesis.

Everything here is regenerated by `scripts/analysis/eval_embed_models.py`.

## Verdict

Keep `all-MiniLM-L6-v2`. It has the joint-best recall@1 and MRR of every
candidate tested, at the smallest size and the lowest latency, and no
alternative beat it by an amount this query set can resolve. The two code-aware
models were the clearest disappointment: the code-specialised jina model was the
*worst* neural arm, and the strong Salesforce code model matched MiniLM while
costing 9.5x the disk, 82x the index build and 21x the query latency. Lexical
retrieval lost, so the neural default is earning its keep, but it earns it on
paraphrase queries specifically.

## Method

**Corpus.** 138 real Claude Code sessions (37,526 events) from
`bdtrace import`, read through the shipped `bdtrace.query.record_text` so every
candidate sees exactly the text the real index sees. Two properties of that text
view matter for reading the numbers:

- 136 of 138 records hit the 2,000-character cap. The median session shows the
  index about 10% of its own text, and the bottom decile shows 0.4%.
- 58 records (42%) fall into 24 groups whose visible text is byte-identical,
  because the SWE-bench-style task prompts repeat verbatim and the cap truncates
  before they diverge. No gold session sits in such a group, so gold labels stay
  unambiguous, but those records act as distractors that no retriever can split.

**Queries.** 60 queries over 30 gold sessions. For each gold session an anchor
was chosen mechanically: a token in that session's `record_text` with corpus
document frequency 1 (a filename, a rare command, a distinctive setting name).
Two queries were then hand-written from the surrounding text and frozen in the
script before any model ran:

- **literal** reuses the anchor wording verbatim, as a user who half-remembers
  the exact string would type it.
- **paraphrase** describes the same session in outside words, avoiding the
  anchor, as a user who remembers only what the session was about.

Gold is established independently of every model under test: it is the session
the anchor string came from, verified unique by document frequency.

**The bias this introduces, stated plainly.** Anchor-derived queries favour
lexical matching, and the literal slice does so heavily: 91.5% of a literal
query's terms appear verbatim in its gold session, against 40.5% for a
paraphrase query. A results table pooled over both slices therefore flatters
BM25 and any model that leans on surface overlap. That is why every result below
is also split by slice, and why the paraphrase slice is the one to read when
asking whether an embedding model understands the corpus.

**Metrics.** recall@1, recall@5 and MRR over all 138 candidates, with 95%
percentile bootstrap intervals over queries (10,000 draws). Model-versus-model
comparisons use a *paired* bootstrap, resampling the same query indices for both
arms, since every arm answered the identical queries. Chance is 0.007 for
recall@1 and 0.036 for recall@5.

**Ties are handled by expectation, not by argsort.** BM25 scores most of the
corpus exactly 0.0, so a plain `argsort` hands the gold a rank determined by its
row number. An earlier version of this script asserted permutation invariance
and caught exactly that: BM25's recall@1 moved 1.7 points with candidate order.
Each query's contribution is now the closed-form expectation over the tied band,
which is deterministic and order-invariant. The realised argsort spread is kept
in the JSON as a diagnostic.

**Decoding parameters.** `normalize_embeddings=True`, batch size 256 (matching
`bdtrace.query.EMBED_BATCH`), float32, CPU, no query prefix except where a model
card documents one. `bge-small-en-v1.5` is reported both with and without its
documented query instruction rather than reporting the better of the two.

**No neural alternative separates from the incumbent.** Every neural interval
straddles zero. With 60 queries this design cannot resolve differences smaller
than roughly 13 points of recall@1, and the four neural candidates sit inside 4
points of each other. The honest statement is not "MiniLM is best" but "MiniLM
is at the top of a group this experiment cannot rank internally, and it is the
cheapest member of that group."

**The lexical baselines do separate, downward.** TF-IDF's interval excludes zero
outright and BM25's MRR interval does too. Lexical retrieval is not a hidden
winner on this corpus.

## Where the difference actually lives

Split by slice, recall@1:

| Arm | literal | paraphrase | gap |
|---|---|---|---|
| all-MiniLM-L6-v2 (incumbent) | 0.942 [0.85, 1.00] | 0.508 [0.33, 0.68] | +0.43 |
| all-mpnet-base-v2 | 0.867 [0.73, 0.97] | **0.567** [0.40, 0.73] | +0.30 |
| SFR-Embedding-Code-400M_R | 0.900 [0.77, 1.00] | 0.500 [0.33, 0.67] | +0.40 |
| bge-small-en-v1.5 | **0.967** [0.90, 1.00] | 0.400 [0.23, 0.57] | +0.57 |
| bge-small-en-v1.5 + query prefix | 0.933 [0.83, 1.00] | 0.433 [0.27, 0.60] | +0.50 |
| jina-embeddings-v2-base-code | 0.800 [0.67, 0.93] | 0.400 [0.23, 0.57] | +0.40 |
| BM25 (lexical) | 0.908 [0.80, 1.00] | 0.300 [0.13, 0.47] | +0.61 |
| TF-IDF cosine (lexical) | 0.842 [0.70, 0.97] | 0.275 [0.13, 0.44] | +0.57 |

This is the finding worth carrying. On literal queries BM25 (0.908) is level
with MiniLM (0.942): if a user remembers the exact filename, grep-shaped
retrieval already answers them and the embedding model is close to redundant.
The neural default earns its cost entirely on paraphrase queries, where MiniLM
reaches 0.508 against BM25's 0.300.

That contrast is also the power check for the negative result above. A paired
bootstrap restricted to the paraphrase slice puts BM25 20.0 points below MiniLM
with P(BM25 better) = 0.025, so the instrument can detect a real 20-point gap on
30 queries. The neural arms failing to separate is a genuine null, not a test
without power.

**Share of queries sitting at the bounds.** 24 of 60 queries (40%) are answered
at rank 1 by every arm and 3 (5%) by none, so only 33 queries (55%) discriminate
between models at all. That concentration is itself a product of the query
construction: 22 of 30 literal queries are solved by everything, against 2 of 30
paraphrase queries. The effective sample for ranking models is therefore much
smaller than 60, which is the main reason the intervals are as wide as they are.

## Cost

Measured on this machine (Apple M-series, CPU, 138 documents). Disk is the
single weight format sentence-transformers loads.

| Arm | dim | context | index build | query latency | disk | licence |
|---|---|---|---|---|---|---|
| all-MiniLM-L6-v2 | 384 | 256 tok | 0.8 s | 2.7 ms | 91 MB | Apache-2.0 |
| bge-small-en-v1.5 | 384 | 512 tok | 3.7 s | 4.8 ms | 134 MB | MIT |
| jina-embeddings-v2-base-code | 768 | 8192 tok | 22.8 s | 22.1 ms | 322 MB | Apache-2.0 |
| all-mpnet-base-v2 | 768 | 384 tok | 7.9 s | 16.7 ms | 438 MB | Apache-2.0 |
| SFR-Embedding-Code-400M_R | 1024 | 8192 tok | 65.2 s | 56.6 ms | 868 MB | **CC-BY-NC-4.0** |
| BM25 | — | — | 0.01 s | 0.2 ms | 0 | — |

Three cost facts that a raw accuracy table hides:

1. **Index build scales with the corpus.** At 138 sessions the difference
   between 0.8 s and 65.2 s is invisible; at 100,000 sessions it is 10 minutes
   against 13 hours on this hardware.
2. **Both code-aware models fail to load on current transformers.** On
   transformers 5.3.0, jina raises `ImportError` on
   `find_pruneable_heads_and_indices` and SFR raises `IndexError` while loading
   weights. Both load on transformers 4.44.2 with sentence-transformers 3.0.1,
   which is the stack this evaluation pinned. Adopting either means pinning
   bdtrace's optional `semantic` extra to a transformers major version that is
   already superseded. Every other arm produces byte-identical metrics on both
   stacks, so the pin is needed to load those two models, not to reproduce the
   comparison.
3. **SFR is CC-BY-NC-4.0, research use only.** That alone disqualifies it as a
   shipped default regardless of its numbers.

## More text does not help, so that is not the lever either

The obvious alternative to changing the model is widening `record_text`, since
it shows the index a median 10% of a session. It does not help:

| Text view | median chars | BM25 recall@1 | jina recall@1 | SFR recall@1 |
|---|---|---|---|---|
| shipped (30 events, 2,000 chars) | 2,000 | 0.604 | 0.600 | 0.700 |
| wider (200 events, 8,000 chars) | 8,000 | 0.583 | 0.467 | 0.683 |
| whole session (uncapped) | 19,849 | 0.500 | not run | not run |

Every arm that can read the extra text gets worse or stays flat, and BM25
degrades steadily as the text grows: more of a session is more distractor
material, not more signal. Widening the cap does fix the 34 duplicate visible
texts, and retrieval still gets worse, so deduplication is not the lever either.

The incumbent's row is omitted deliberately. `record_text` is prefix-monotone
and MiniLM truncates at 256 tokens, so its input is byte-identical across all
three views and its scores cannot move. The script asserts exactly that, as a
check on the diagnostic rather than a result. The uncapped view was not run for
the 8192-token models because of CPU cost; the wider view already fits entirely
inside their context window, so it settles the question.

## Recommendation

**Keep `all-MiniLM-L6-v2` as the default.**

*Benefit:* the joint-best accuracy measured here at the smallest footprint
(91 MB), the fastest index build (0.8 s per 138 sessions) and the lowest query
latency (2.7 ms), on an Apache-2.0 licence and with no dependency pin. It is
also the only candidate whose 384-dimension output keeps the persistent flat
index small, which matters because `bdtrace/index.py` stores float32 vectors per
trace.

*Price:* on paraphrase-style queries MiniLM sits at 0.508 recall@1 while
`all-mpnet-base-v2` reaches 0.567. That 6-point gap is well inside this query
set's noise and should not be acted on, but it is the direction any future gain
would come from, and it is the number to re-measure rather than the pooled one.
MiniLM's 256-token window is also the tightest of any candidate, so it reads
roughly the first 40% of an already-truncated text view; the text-view
experiment says that is currently costless, but it would stop being costless if
`record_text` were ever restructured to put distinguishing content later.

**Do not switch to a code-aware model.** The prior that mixed code and prose
would favour a code encoder is not supported: jina was the worst neural arm
tested, and SFR bought no measurable accuracy for 9.5x the disk, 82x the build
time and a non-commercial licence.

**What would change this recommendation.** A corpus an order of magnitude
larger, where 138-candidate ranking stops being easy and the models have room to
separate; or a shift in how the tool is used toward paraphrase-style queries,
where the arms genuinely differ most. Both are re-measured by rerunning this
script with a larger `--corpus`.

## Caveats

- 138 candidates is a small corpus. Every arm is far above the 0.007 chance
  floor, and easy retrieval compresses differences. These results should not be
  extrapolated to a corpus 100x larger without re-running.
- The 60 queries were written by one author from a mechanically selected sample
  of 30 of the 76 eligible sessions. They were frozen before any model ran and
  no query was edited after seeing a score, but they are not an independent
  user-behaviour sample, and real queries would be shorter and vaguer than
  these.
- Timings are single-run on a loaded laptop. Treat the ratios as reliable and
  the absolute milliseconds as indicative.

## Reproducing

```bash
uv run --with "transformers==4.44.2" --with "sentence-transformers==3.0.1" \
  --with "huggingface_hub<0.26" --with rank-bm25 --with scikit-learn \
  --with einops --with numpy \
  python scripts/analysis/eval_embed_models.py \
    --corpus /path/to/all.jsonl --bootstrap 10000 --out results.json
```

Drop the version pins to run everything except the two code-aware models, which
will report themselves unavailable with the load error; all other numbers are
unchanged. `--skip-text-view` omits the `record_text` width diagnostic, which is
most of the runtime.
